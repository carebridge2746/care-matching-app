# supabase/tests — 스키마 검증 스크립트

`supabase/schema.sql` 의 권한·상태 규칙이 실제 데이터베이스에서 그대로 지켜지는지 확인하는 SQL 스크립트입니다.
앱을 거치지 않고 함수와 정책을 직접 부르므로, 화면이 아니라 데이터베이스가 규칙을 지키고 있는지를 봅니다.

## 스크립트

| 파일 | 확인하는 것 | 검사 수 |
| --- | --- | --- |
| `01_roles_and_admin_guard.sql` | 가입 metadata 로 관리자가 될 수 없음 · 본인 role/email 변경 차단(이름은 허용) · 운영자 경로의 관리자 지정 · `is_admin()` · 비관리자의 `admin_*()` 호출 거부(42501) · `admin_actions` 비공개 · `log_admin_action` 실행 권한 없음 | 23 |
| `02_care_flow.sql` | 보호자의 환자·요청 등록(RLS) · 수락/중복 수락 · 시작은 당사자 간병인만 · 종료 · 종료 후 취소 불가 · 시작 전 취소는 요청 재오픈 · 시작 후 취소는 요청 종료 · 노쇼 신고(보호자만, 시작 전만, 시작일 당일부터) · 노쇼 간병인의 재수락 차단과 추천 제외 · 시작일 전 시작 차단 | 25 |
| `03_reviews_reports_admin.sql` | 후기(끝난 매칭만, 1인 1회) · 신고(당사자만, 중복 null, 사유 검사) · 관리자 후기 삭제/복구와 평균·목록·추천 반영 · 신고 기각 · 분쟁 매칭 목록 · 노쇼 되돌리기 · 강제 취소 · 감사 로그 | 34 |

세 파일은 서로 의존하지 않습니다. 순서와 상관없이 하나씩 따로 실행해도 됩니다.

## 실행 방법

1. `schema.sql` 이 적용된 Supabase 프로젝트의 **SQL Editor** 를 엽니다.
2. 스크립트 파일 하나의 내용을 통째로 붙여넣고 실행합니다.
3. SQL Editor 의 역할 선택(role)은 기본값인 `postgres` 로 둡니다. 스크립트가 필요한 사용자로 직접 바꿔 가며 실행합니다.

각 스크립트는 `begin; ... rollback;` 으로 감싸져 있습니다. 테스트 계정(`auth.users`)·요청·매칭·후기·감사 로그는
모두 같은 트랜잭션 안에서 만들어졌다가 마지막 `rollback` 으로 사라지므로, 운영 중인 프로젝트에 실행해도 데이터가 남지 않습니다.

### 사용자 흉내 내기

스크립트는 아래 두 줄로 로그인한 사용자를 흉내 냅니다. Supabase 의 `auth.uid()` 는 `request.jwt.claims` 의 `sub` 를 읽습니다.

```sql
set local request.jwt.claims to '{"sub":"<uuid>","role":"authenticated"}';
set local role authenticated;
```

운영자(SQL Editor)로 돌아올 때는 `reset role;` 과 함께 claims 를 비웁니다. 비우지 않으면 `auth.uid()` 가 마지막 사용자로 남습니다.

## 출력 읽는 법

- 검사를 하나 통과할 때마다 `NOTICE: PASS: <검사 이름>` 이 남습니다. 마지막에 `<파일명>: 모든 검사 통과 (N개)` 가 나옵니다.
- 기대와 다르면 `ERROR: FAIL: <검사 이름> (...)` 예외가 나고 **그 자리에서 멈춥니다.** 괄호 안에 실제 값이나
  `예상 42501, 실제 <SQLSTATE> <메시지>` 가 붙습니다. 뒤의 검사는 실행되지 않으며 트랜잭션은 통째로 취소됩니다.
- SQL Editor 가 NOTICE 를 보여 주지 않는 경우도 있습니다. 그때는 **오류 없이 끝났다면 모든 검사를 통과한 것**입니다.
- 실패한 뒤 다음 실행에서 `current transaction is aborted` 가 나오면 `rollback;` 한 줄을 먼저 실행하고 다시 돌립니다.

## 알아 둘 점

- 테스트 계정 id 는 파일마다 고정값(`10000000-…`, `20000000-…`, `30000000-…`)이고 이메일은 `t0N-…@example.test` 입니다.
  같은 id 나 이메일이 이미 있는 프로젝트라면 준비 단계의 insert 가 실패합니다.
- 노쇼·분쟁 매칭 검사는 한국 시간(`Asia/Seoul`) 기준 오늘 날짜로 시작일·종료일을 만들어 넣습니다.
- `admin_review_reports()` 와 `admin_disputed_matches()` 는 최대 100줄, `recommendation_candidates()` 는 최대 50줄만 돌려줍니다.
  열린 신고나 분쟁 매칭이 이미 100건 넘게 쌓인 프로젝트에서는 03 의 해당 검사가 잘려서 실패할 수 있습니다.
  (추천은 테스트 간병인의 경력을 최댓값 60 으로 넣어 목록 앞쪽에 오게 했습니다.)
- `schema.sql` 의 함수 규칙을 바꾸면 해당 스크립트의 기대값도 함께 고칩니다. 같은 함수가 파일 안에서 여러 번
  다시 정의되는 경우(`accept_care_request`, `recommendation_candidates` 등) 검사는 마지막 정의를 기준으로 합니다.
